现在做 Agent 的人几乎都会碰到同一个问题。模型上下文越来越大，推理也越来越强，但一到私有知识或长期记忆，大家还是习惯性把 RAG 当成默认答案。任何检索都先上向量库，任何记忆都先分块 embedding。这条路走得太顺了，以至于很多人忘了问一句：真的需要这么重吗？

2025 年前后，几乎所有 Agent 教程都会告诉你先建一个向量知识库。用户提问，先检索相关片段，再塞进 prompt 生成。这套流程在简单问答上确实有效，但一旦任务变复杂，或者知识在快速变化，它的问题就暴露出来了。检索质量完全依赖分块和 embedding，模型没有机会自己决定要不要查、查什么、查几次。上下文被一堆半相关的 chunk 填满后，真正有用的信号反而被淹没。更麻烦的是，很多团队把所有东西都默认做成 RAG，包括本来可以直接放进上下文的小规模事实，或者本来应该用工具调用解决的结构化查询。

Anthropic 内部的数据 Agent 给出了另一种思路。他们没有给 Claude 挂一套传统 RAG 流水线，而是用两套 skill 来完成几乎相同的事。一套 knowledge skill 讲清楚表结构、语义层和指标定义，另一套 runbook skill 教模型怎么分析、怎么预测、什么时候该拒绝噪声数据。skill 文件直接挂在磁盘上，每次对话重新读取，模型按需加载。上下文窗口够大之后，这种程序性知识加按需披露的方式，比把所有文档先切碎再向量检索更干净。模型自己决定什么时候加载哪份 skill，加载到什么深度。这本质上是把检索从固定流水线，变成了 Agent 可自主调用的行为。

同一时期，开源 Agent 框架也在做类似取舍。OpenClaw 和 Hermes 对记忆的处理方式差异很大，但它们都没有走重 RAG 的老路。

OpenClaw 把记忆落在 Markdown 文件里。MEMORY.md 存长期事实和决策，daily notes 按日期记当天内容。检索时走的是混合方案。文件变更后会分块、做 embedding，同时建 FTS5 关键词索引。调用 memory_search 这个 tool 时，系统并行跑向量相似度和 BM25，按大概七三的权重合并，再叠加时间衰减和重要性，最后用 MMR 去冗余。返回的是带路径和行号的 snippet，不是整份文件。它本质上是轻量 RAG，但做得克制。索引是增量更新的，搜索只查已经建好的索引，不会在每次调用时重新切文件。Agent 自己决定什么时候调用这个 tool，就像调用 shell 或读文件一样。没有强制每次提问都走一遍向量流水线。

Hermes 走了另一条路。它把真正重要的记忆压进两个有硬上限的文件。MEMORY.md 大约 2200 字符，USER.md 大约 1375 字符，直接塞进 system prompt，不检索。这些内容在会话开始时就固定下来，保证前缀缓存稳定。历史会话则全部进 SQLite，用 FTS5 做全文搜索，召回后再让模型摘要。默认路径里没有向量库，没有 embedding。只有挂上外部 memory provider 时，才会变成语义检索。它故意把永远在上下文里的东西，和需要时再去查的东西，分得很清楚。小规模、高价值的事实直接住在 prompt 里，大规模历史用关键词搜索按需召回。

两者都不是 2023、2024 年那种重 RAG。OpenClaw 是轻量混合检索，Hermes 是关键词全文搜索加强制策展。Agent 自己决定什么时候调用检索 tool，而不是每次提问都强制走一遍向量流水线。上下文窗口变大、模型变聪明之后，真正需要的不是更重的 RAG，而是更克制的知识注入方式。

把这个思路放到更实际的场景里。假设手里有一万个混合文件，PDF、Word、Markdown、图片都有，要建成可用的知识库，该怎么设计？

解析是真正的瓶颈。不同类型必须分流，绝不能用一个通用 parser 硬吃所有格式。Markdown 直接读，保留标题层级。PDF 优先用 layout-aware 的解析器，能识别标题、段落、表格和列表的那种。扫描件再上 OCR。Word 用能保留样式和标题树的库。图片用视觉模型生成描述，同时跑 OCR 提取文字，描述里尽量包含关键数值和趋势，并挂上原图路径。统一输出带元数据的文本块，失败就记日志跳过，不要硬撑。解析质量直接决定后面所有步骤的上限，这里省事后面会加倍还。

分块策略决定检索准确率。固定 token 硬切是最容易也最差的办法，它会把结论和前提拆开，把完整逻辑切断。正确的做法是结构优先。有标题树就按标题路径切，一个二级标题下的内容尽量放在一起，超过上限再按段落切。目标长度控制在 400 到 800 token，重叠 10 到 20%。表格单独成块，或者转成 Markdown 后作为独立 chunk 处理。超大表格按行切，并保留表头。图片描述作为独立 chunk，元数据里必须带原图路径和页码。每个 chunk 强制携带 source_path、file_type、page 或 location、heading_path。这些信息比单纯的语义向量重要得多，检索时可以过滤，回答时可以溯源。

代码块需要特殊对待。优先相信上游解析器已经识别出的结构。Markdown 的围栏、好的 PDF 解析器标出的代码元素，直接完整保留，绝不跨块切断。解析器没识别出来时，才用轻量脚本补充判断。检查缩进一致性、关键词密度、特殊符号比例、行长度分布。满足阈值就当成代码块处理，强制保持完整。不要每个疑似块都丢给大模型判断，成本和延迟都会炸。规则加结构优先，模型只做兜底。

检索层继续保持轻量。向量加 BM25 混合是默认，不要一上来就上复杂的 agentic 多跳。元数据过滤、简单 rerank、出处返回，这些就够用了。一万文件规模用单机向量库完全能撑住，增量更新比全量重建重要得多。索引跟着文件变更自动更新，解析失败率和低分检索都要可观测。

整条链路的核心顺序其实很清楚。先把解析做对，再谈分块。分块尊重结构，再谈 embedding。检索用混合而不是纯向量。Agent 侧把检索当成可调用的 tool，而不是固定流水线。上下文窗口变大、模型变聪明之后，真正需要的不是更重的 RAG，而是更克制的知识注入方式。

OpenClaw 和 Hermes 已经在这个方向上给出了不同答案。一个选择轻量混合检索，一个选择极小记忆加全文搜索。两者都证明，默认把所有东西都塞进向量库，并不是唯一解，甚至不是最优解。知识库真正难的地方从来不在向量模型本身，而在解析质量、分块策略和检索时机的选择。把这些基础做扎实，后面的 Agent 才会真正有用。

回到我们的主题，
大多数时候不该用，至少不该默认用。
RAG 解决的是两个真实问题：模型知识过时，上下文装不下。就这两个。其他所有吹捧都是衍生出来的。
更深一层看，现在的模型上下文已经够大，推理也够强。很多以前必须靠检索的场景，直接塞文件、用工具、或者写 skill 就够了。强制上 RAG，等于主动引入额外失败点：检索不准、上下文污染、延迟上升、成本翻倍、调试变难。
真正该问的问题不是"要不要 RAG"，而是：

- 这个知识变不变？
- 规模有多大？
- 需要可溯源吗？
- 模型能不能自己决定要不要查？

稳定小规模事实，直接放 prompt 或 skill。
结构化数据，用 SQL 或工具。
海量动态非结构化文档，且必须出处，才值得上轻量混合检索。
其他情况，上 RAG 就是工程偷懒。

OpenClaw 那种轻量混合、Hermes 那种极小记忆加全文搜索，已经证明更克制的路线可行。Anthropic 用 skill 替代传统 RAG，也是同一逻辑。
RAG 不是死了，它只是从默认架构，降级成了特定场景下的工具。继续把它当万能解，才是真正的问题。
