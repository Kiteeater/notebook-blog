AI Native 项目的核心变化，不是代码量变多，而是代码的生成方式和理解方式同时失效。当模型负责写出大量实现，源码很快变成黑盒。人读不动，agent 也读不全。这时候，工程可视化不再是锦上添花，而是系统能否被理解和被迭代的前提。

代码只是计划。它描述的是"我打算怎么做"。真正决定系统行为的是运行时的执行路径：真实输入、并发、模型的不确定性、生产状态、tool 返回的各种边界情况。这些东西叠加之后，静态阅读源码的性价比急剧下降。你以为 A 只调了 B，实际 trace 里可能出现了 C、D，甚至出现了意料之外的重试和回退。计划与事实的差距，就是架构漂移的起点。

所以可视化的重点不是再多画几张架构图，而是把执行本身变成可观察、可查询、可对比的对象。Observability 从运维工具升级成 AI 工程的基础设施。它的价值不在于"多记点日志"，而在于用宽事件把一次请求的完整上下文留下来。

宽事件的意思很简单：每个请求或每个关键函数调用，发出一条高维结构化记录。字段可以任意扩展——用户 ID、区域、参数、输出、延迟、错误信息、模型名称、token 数、重试次数。关键是保留类型，而不是把一切都拍成字符串。字符串看起来方便，查询时却会失去精度。只有结构化，事后才能用接近写代码的方式直接提问。

一个典型的图像生成链路会变成这样一条执行树：生成函数先构建 prompt，再调用大模型，进入评价循环，最后通过 HTTP 发出结果。每个节点都带着输入、输出、耗时和状态。大模型调用还会自动记录输入输出，并对相同的大对象做去重，避免数据膨胀。查询可以写成"找出参数长度超过 50 且延迟超过 1 秒的生成调用"。schema 是感知的，人和 agent 都能直接使用。

有了这些数据，架构问题不再需要猜。火焰图把调用栈的时间占比直接画出来。横轴是时间占比，纵轴是调用深度。宽的块就是真正耗时的地方。你不用先读懂代码，就能知道时间都去了哪里。Call stack 则是函数调用链本身：A 调 B，B 调 C，当前停在 C。在 trace 里它变成父子 span 构成的树。同一服务内的调用、跨服务的依赖，都能通过这棵树看到。源码写的是"我只依赖这个接口"，trace 显示的却可能是三条额外的路径。运行时真相和静态代码的差距，就这样被暴露出来。

这种结构尤其适合 agent 和 tool 调用链路。每个 MCP 或工具调用都是一个 span。参数、返回值、耗时、是否报错、重试次数全部落在树上。整条决策链变成可视化的对象：先调了哪个工具，返回了什么，再决定下一步。失败点直接暴露，不需要再去翻源码猜测逻辑。

Agent 确实能分析这些 trace，但前提是数据足够结构化，并且先做过滤。长 trace 直接塞进上下文会稀释注意力，这是真实限制。正确做法是让 agent 先筛出异常 trace——错误、超时、高延迟、重试过多——再对局部路径做分析或摘要。人只需要看被标记的关键路径，而不是全量人工 review。生产行为因此变成 agent 的下一轮反馈信号。它可以直接问"这次请求里 HTTP 调用了几次""哪一层延迟最高"，再对比设计时的预期调用栈和实际执行，找出偏差并改进代码。没有这个闭环，agent 就只是在真空里改代码；有了这个闭环，它才真正在学习系统真实的行为。

OpenTelemetry 把这些概念落实成具体的数据结构。Trace 是一次完整请求的全部旅程，共享同一个 Trace ID。Span 是旅程中的一个工作单元，带有自己的 Span ID 和父 Span ID。多个 Span 通过父子关系组成树。

模拟一个用户请求"生成一张猫的图片并评价"：

```
Trace ID: abc123-xyz789

└── agent.handle_request                (总耗时 4.8s)
    ├── llm.chat (第一次思考)            (1.2s)
    │     model = claude-4
    │     input_tokens = 320
    │     output_tokens = 85
    │     prompt = "用户要生成猫图并评价..."
    │
    ├── tool.generate_image             (2.6s)
    │     ├── http.send                 (2.4s)
    │     │     url = "https://api.xxx/generate"
    │     │     status_code = 200
    │     │     latency_ms = 2410
    │     tool_name = generate_image
    │     args.prompt = "a cute cat..."
    │     output.image_id = "img_987"
    │
    ├── llm.chat (第二次思考+评价)       (0.9s)
    │     model = claude-4
    │     input_tokens = 680
    │     output_tokens = 45
    │
    └── agent.return_response           (0.1s)
```

每个 Span 至少包含 trace_id、span_id、parent_span_id、名称、起止时间、状态，以及任意 attributes。树的宽度显示时间花在哪里，深度显示调用有多深，父子关系暴露真实依赖。出错时直接看哪个 Span 状态是 Error，往上追父节点就能定位整条链路。

代码是计划，trace 是事实。把系统建成"执行本身就是真相"的样子，人和 agent 才能从猜测转向调查。Tracing 必须从一开始设计进去。事后补永远太晚，信息已经丢失，反馈信号也不再干净。

AI Native 项目的工程可视化，本质上是在回答一个更根本的问题：当代码不再完全由人写、也不再完全被人读的时候，我们如何仍然对系统保持理解和控制。答案不是更努力地读代码，而是让执行过程变得可见、可查询、可反馈。
